# PGR_Make 0.4 — интеграция ядра и улучшенный GTK4

## Назначение

Проект сохраняет размещение относительно исполняемого файла:

```text
C:\PGR\
  PGR_Make.exe          # CLI / TUI
  PGR_Make_GUI.exe      # GTK4
  Pack\                 # GCC, Clang, CMake, Ninja, GTK4 runtime, toolchain
  Project\              # независимые настройки зарегистрированных проектов
      Calculator\
        project.pgr
        config.cfg
        diagnostics.json
        history.log
        history\          # снимки диагностик по сборкам
```

Исходники проектов остаются в выбранных пользователем каталогах.
Новые функции не требуют миграции `project.pgr` или `config.cfg`.

## Что изменено по сравнению с GTK4 Paned

### Общее ядро

- `core/build_controller.hpp` — единый код **прямой и CMake-сборки** для CLI и GTK4. Принимает проект, режим, настройки, callback вывода и отмену. Управляет диагностикой и историей.
- `core/process_runner.hpp` — запускает процессы без командной оболочки; принимает явную рабочую директорию; позволяет остановить процесс и его потомков. Windows: Job Object; Linux/POSIX: группы процессов, а на Linux также поиск потомков через `/proc` при отмене.
- `core/toolchain_manager.hpp` — поиск конкретных инструментов по абсолютным путям с предпочтением выбранного комплекта из `Pack`, без изменения глобального `PATH` в GUI/CI. При отсутствии инструмента в Pack допускается системный PATH с явным сообщением в GUI.
- `core/json_reader.hpp` — строгий ограниченный парсер JSON, применяемый к схеме `diagnostics.json`. Отказ от разбора структурированного JSON регулярными выражениями. Поддерживаются экранирование и Unicode `\u`, в том числе surrogate pairs.
- CMake-флаги `-Os/-Wall/-Wextra` больше не передаются MSVC при сборке самого PGR_Make.

### GUI

- Текущий `GtkPaned` сохранён: слева полный конфигуратор, команды, журнал, диагностика и история; справа список проектов.
- Добавлены поиск по разделам конфигурации, поиск проектов по названию и пути.
- Главная кнопка «Собрать» с выбором режима: PGR CMake / собственный CMake / прямой компилятор.
- Форма показывает, есть ли несохранённые изменения. Переключение проекта предлагает «Сохранить», «Без сохранения», «Отмена». Отдельно доступен явный сброс изменений.
- Все операции сборки выполняются в рабочем потоке. Окно не должно блокироваться на выводе компилятора; события приходят в главный поток GTK через GLib idle callback.
- «Остановить» использует сигнал отмены для контроллера процессов, не просто уничтожает окно консольной программы.
- В диагностике доступны фильтры ошибок/предупреждений, копирование выделенной строки и переход к исходнику через VS Code или системную ассоциацию.
- Отдельная вкладка «История» показывает результаты и продолжительность прошлых сборок.
- Менеджер проектов умеет переименовать запись, изменить путь, клонировать конфигурацию и архивировать запись без удаления исходников. Недоступные исходники отображаются вместо исчезновения из списка.
- Через кнопку проверки Pack можно посмотреть список обнаруженных инструментов и версии в журнале.

### Реестр проектов и защита данных

- Удаление проекта из списка **архивирует метаданные** в `Project/.pgr_archived/`, не удаляет исходные файлы и прежние каталоги сборки.
- Переименование проекта не удаляет исходники. Старые выходные артефакты и каталоги `.pgr_build/<старое имя>` остаются на диске.
- Клон проекта получает отдельную папку конфигурации, а его исходники могут быть общими с оригиналом. При клонировании следует проверить `output_file` прямой сборки, чтобы результаты не перезаписывали друг друга.
- Очистка по-прежнему требует маркер принадлежности каталога сборки PGR_Make.

## Сборка (Windows, MSYS2 UCRT64)

Установите GCC, Ninja, CMake, pkgconf, GTK4 development files. В MSYS2 UCRT64, например:

```sh
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gtk4 mingw-w64-ucrt-x86_64-pkgconf mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja
```

Затем:

```sh
cmake -S . -B build-win -G Ninja -DCMAKE_BUILD_TYPE=Release -DPGR_BUILD_GUI=ON -DPGR_REQUIRE_GUI=ON -DPGR_STATIC_WINDOWS=ON
cmake --build build-win --parallel
ctest --test-dir build-win --output-on-failure
```

Результаты сборки: `PGR_Make.exe` и `PGR_Make_GUI.exe` в `build-win`.
CLI/основная C++ runtime может быть статически слинкована, но **GTK4 на Windows использует динамические библиотеки**, которые нужно поставлять вместе с GUI; см. `GUI_GTK4.md`, `tools/bundle_gtk_runtime.ps1`.

Не переписывайте каталог `Project` при обновлении. Сначала создайте резервную копию `C:\PGR\Project`, затем замените исполняемые файлы и при необходимости обновите `Pack\GTK4`.

## Тестирование и ограничения

Доступная Linux-среда: GCC 14, CMake, Ninja. Пройдены девять групп CTest, включая интеграционные Python-проверки C/C++, Pack, прямой/CMake-сборки, владения каталогами, историю, JSON, регистрацию и отмену потомков процесса.

**Не подтверждены в данной среде:** нативная компиляция/запуск GTK4, MSVC, статическая линковка Windows и runtime GTK4 в `Pack`. Проверка текста исходника `test_gui_surface.py` не является настоящим GUI-тестом. MSVC требует подготовленного окружения Visual Studio (Developer Command Prompt/vcvarsall); полностью автоматическое обнаружение и настройка Visual Studio не реализованы.

Пока также не реализованы автоматизированные UI-тесты с управлением настоящим GTK4-окном и постоянный LSP-сеанс. Анализ clangd работает по запросу, как и прежде. Работа с `Pack` в CLI/TUI частично сохраняет наследуемую логику PATH ради обратной совместимости; сборки GUI/CI используют разрешение конкретного компилятора.
