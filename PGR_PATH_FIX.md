# PGR_Make 0.5: исправление путей в генерируемом CMake

## Что происходило

GTK4 GUI запускается обычно из `C:\PGR`, а исходники зарегистрированного
проекта располагаются в другой директории. Ранее `cmake_writer_t::abs_path()`
вычислял абсолютные пути относительно **текущего каталога процесса**. В итоге
сгенерированный CMake ссылался на `C:/PGR/main.cpp`, `C:/PGR/gui/main.cpp`
и другие несуществующие исходники.

## Что изменено

`core/cmake_writer.hpp` использует корень `tree.root()` для всех относительных
путей при генерации CMake. Путь передаётся явно через методы генератора;
сам `current_path()` не изменяется. Это важно для GUI, который может
переключаться между несколькими проектами.

Проверяются пути к исходникам, каталогам заголовков и библиотек,
CMAKE_PREFIX_PATH, toolchain-файлам, linker scripts и выходным файлам.

Добавлен регрессионный тест `tests/test_cmake_project_root.cpp`, который
запускает генератор при отличающихся рабочем каталоге приложения и корне
исходников. Он проверяет корневой и вложенные `CMakeLists.txt`.

## Как восстановить сборку

1. Замените файлы программы этой версией и пересоберите `PGR_Make_GUI.exe`.
2. В PGR_Make выберите нужный проект с корректным `source_root`.
3. Для проекта PGR_Make рекомендуется режим «Существующий CMakeLists.txt»,
   так как штатный CMake-файл описывает GTK4-зависимости.
4. Если ранее сохранился неудачный CMakeCache, очистите только
   принадлежащий PGR_Make каталог сборки через меню GUI или опцию `--clean`.

Оригинальные исходники и `CMakeLists.txt` в директории проекта не заменяются.

## Проверки

- `cmake --build`: успешно (GCC, Linux; CLI)
- `ctest --output-on-failure`: 11/11 успешно
- конфигурация и сборка тестового проекта через сгенерированный CMake + Ninja:
  успешно с независимой директорией GUI и пробелами в пути

Полная компиляция GTK4 под Windows здесь не проводилась: GTK4 SDK и
Windows-компилятор недоступны. Требуется проверить на целевой машине.
