# PGR_Make — переносимый менеджер сборки C/C++

Версия с **реестром проектов**, отдельным каталогом инструментов и **статической линковкой самого PGR_Make.exe** на MinGW UCRT64.

## 1. Структура установки

```text
C:\PGR\
  PGR_Make.exe            # автономное TUI-приложение (после сборки под Windows)
  Pack\                   # внешние инструменты (пользователь устанавливает сам)
    GCC\bin\g++.exe
    GCC\bin\gcc.exe
    LLVM\bin\clang++.exe
    CMake\bin\cmake.exe
    Ninja\ninja.exe
  Project\                # реестр конфигураций, отдельно от исходников
    Calculator\
      project.pgr          # привязка к каталогу исходников
      config.cfg           # опции компиляции
      profiles\
      work.log
      generated_cmake\    # служебная CMake-генерация
```

Исходники, например `D:\Development\Calculator\src\main.cpp`, располагаются **где угодно**, при наличии прав доступа. Рабочий каталог запуска не важен. Имя проекта может содержать кириллицу и пробелы (но не запрещённые в Windows символы пути); пути к исходникам тоже могут содержать пробелы.

Существующие `CMakeLists.txt` в каталоге исходников не перезаписываются. При новой генерации пересоздаётся только `C:\PGR\Project\<имя>\generated_cmake`.
Начиная с данной версии, этот каталог должен содержать маркер принадлежности PGR_Make; неизвестный непустой каталог программа не удаляет.

В `Pack` **нет инструментов по умолчанию**. Положите туда целые, работоспособные дистрибутивы GCC, Clang, CMake, Ninja или cross-toolchain, включая необходимые им runtime DLL. Указанные `bin`-каталоги автоматически добавляются **перед системным PATH** на время выполнения PGR_Make. Поддерживаются `Pack/bin`, `Pack/<tool>/bin`, `Pack/<tool>/ucrt64/bin`, `Pack/<tool>/mingw64/bin` и `Pack/<tool>/<nested>/bin`. При отсутствии пакета возможен fallback в системный `PATH`.

## 2. Сборка статического PGR_Make.exe для Windows

Нужна среда **MSYS2 UCRT64**, установленный C++17-компилятор GCC, CMake и Ninja. Из терминала `MSYS2 UCRT64` можно запустить:

```sh
cmake -S . -B build-win -G Ninja -DCMAKE_BUILD_TYPE=Release -DPGR_STATIC_WINDOWS=ON
cmake --build build-win
```

Или из командной строки Windows, где инструменты MSYS2 UCRT64 присутствуют в `PATH`:

```bat
build_windows.bat
install_to_c_pgr.bat
```

`build_windows.bat` копирует `build-win/PGR_Make.exe` в `deploy/PGR/PGR_Make.exe`; `install_to_c_pgr.bat` устанавливает/обновляет только **exe** в `C:\PGR` и создаёт недостающие папки. **Содержимое `C:\PGR\Pack` и `C:\PGR\Project` не удаляется и не перезаписывается установщиком.**

`main.bat` собирает Windows-версию и запускает её из `deploy/PGR`. В архиве исходников **готового Windows EXE нет**; он формируется при запуске указанных команд на Windows. На Linux/macOS можно собирать программу с CMake без Windows-линковки.

Опция `PGR_STATIC_WINDOWS=ON` добавляет для MinGW флаги `-static -static-libgcc -static-libstdc++`. Проверьте зависимости командой:

```bat
objdump -p build-win\PGR_Make.exe | findstr "DLL Name"
```

Статическая линковка **не** включает GCC, Clang, CMake, Ninja в `.exe` и **не** избавляет инструменты из Pack от их DLL. Системные Windows DLL импортируются обычным образом.

## 3. Первый запуск

1. Запустите `C:\PGR\PGR_Make.exe` двойным щелчком или через терминал.
2. В меню проектов выберите номер уже зарегистрированного проекта либо `N` (**создать**).
3. Для нового проекта укажите уникальное **имя** и **папку исходников** (например `D:\Projects\Calculator`). Несуществующий каталог создаётся; при желании программа создаст пример `main.cpp`.
4. Откроется конфигуратор TUI именно для этого проекта. Укажите компилятор, стандарт, исходники, include-пути и остальные параметры. Выберите **17** для прямой сборки или **19** для сборки через генерируемый CMake (перегенерация теперь выполняется автоматически). Пункт **32** собирает существующий `CMakeLists.txt` из каталога исходников, не изменяя его.
5. Пункт **31** позволяет явно выбрать найденный компилятор из `Pack` и записать его абсолютный путь в конфигурацию. Пункт **30** возвращает к выбору проектов; **0** завершает программу. Параметры сохраняются независимо для каждого проекта.

Конфигурационные файлы хранятся **внутри установки**, в `C:\PGR\Project\<name>\config.cfg`, а не в каталоге исходников. Логи и отдельные профили также изолированы.

## 4. Командная строка и автоматизация

```sh
PGR_Make.exe --list
PGR_Make.exe --toolchains
PGR_Make.exe --create Calculator --source-dir "D:/Projects/Calculator" --starter
PGR_Make.exe --project Calculator
PGR_Make.exe --project Calculator --ci
PGR_Make.exe --project Calculator --ci --clean --build-dir build_cmake
PGR_Make.exe --project Calculator --ci --profile debug
PGR_Make.exe --project Calculator --ci --native-cmake
```

`--create` создаёт запись в `Project` и конфигурацию. `--starter` добавляет `main.cpp`, только если `main.cpp` и `src/main.cpp` отсутствуют; существующие исходники не перезаписываются. Если файлы уже есть, программа пытается найти C/C++-исходники рекурсивно, исключая каталоги сборки. При необходимости скорректируйте `source_files` через TUI. `--project NAME` открывает проект в конфигураторе, `--ci` запускает неинтерактивную сборку по сохранённой конфигурации. `--home PATH` переопределяет корневую папку установки для тестирования/переносимой эксплуатации.

Для проекта `Calculator` CMake генерируется в `C:\PGR\Project\Calculator\generated_cmake`. Итоговая сборка по умолчанию располагается **в директории исходников** в `.pgr_build/Calculator`; для разных записей проектов, даже при общей папке исходников, используются отдельные каталоги. Прямой режим использует `output_file` из конфигурации (например `build/Calculator.exe`). CI копирует `compile_commands.json` в хранилище конфигурации `C:\PGR\Project\Calculator`, не перезаписывая файл исходного проекта. Пункт **25** в TUI экспортирует файл в корень исходников только если такого файла там ещё нет.

Путь `--build-dir` для CI может быть абсолютным либо относительным, но обязан разрешаться **внутрь** исходного проекта и быть безопасным. `--clean` допускается только с `--ci`. Удаление возможно **только для каталогов сборки с правильным маркером `.pgr_make_build_owner`**, содержащим идентификаторы конкретного проекта и исходного дерева. Чужие, непустые, неразмеченные каталоги не трогаются. Это защита от случайного удаления, а не механизм против преднамеренной подделки маркера. Пути с промежуточными символьными ссылками отклоняются. Выполнение команд производится без командной оболочки (`CreateProcessW` на Windows, `fork/execvp` на Linux).

## 5. Формат конфигурации

```ini
compiler=g++
source_files=main.cpp
source_files=src/helper.cpp
output_file=build/Calculator.exe
standard=-std=c++17
optimization=-O2
warnings=-Wall
warnings=-Wextra
include_dirs=include
library_dirs=external/lib
libraries=pthread
# Опционально: toolchain_file=cmake/arm-none-eabi.cmake
# Опционально: linker_script=linker.ld
# Опционально: c_standard=-std=c11
# Опционально: target_type=shared
```

Для смешанного C/C++-проекта прямой режим сначала компилирует `.c`-файлы отдельным C-компилятором (gcc/clang), затем компонует вместе с C++-исходниками. Для чистого C-проекта можно указать `compiler=gcc` и `c_standard=-std=c11`. Toolchain-файл используется генератором CMake; встроенные стандартные наборы флагов компилируются в приложение (`core/builtin_flags.hpp`) и не требуют `config/*.txt` рядом с исполняемым файлом.

## 6. Разработка и тестирование

Код: `main.cpp` — меню выбора, CLI и CI; `core/workspace.hpp` — реестр проектов и пути; `core/pack_tools.hpp` — поиск инструментов в Pack; `core/TUI.hpp` — конфигурация; `core/make.hpp` — прямая сборка; `core/cmake_writer.hpp` — генератор CMake; `core/tree.hpp` — дерево исходников; `core/safe_paths.hpp` — безопасная очистка; `core/cmake_session.hpp` — управление кешем CMake; `core/toolchain.hpp` — согласованное определение C/C++ компиляторов.

```sh
cmake -S . -B build-review -G Ninja
cmake --build build-review
python tests/run_tests.py ./build-review/PGR_Make
```

Проверки покрывают C, C++, пути с пробелами, ASan, include, `#finder`, заголовочные циклы, библиотеки, отдельные профили и конфигурации, интерактивный выбор проекта, запрет опасной очистки, а также приоритет найденного внутри Pack компилятора, маркеры принадлежности сборки, два проекта на одну папку, смешанные C/C++, смену компилятора, исходный CMake и автоматическую регенерацию. В текущей среде программа проверялась на Linux (GCC 14.2); **нативный Windows EXE и работа конкретных toolchain в Pack требуют проверки на Windows**.

## 7. Ограничения

Автоматическое обнаружение целей, модулей и зависимостей остаётся эвристическим. Для больших проектов с нетривиальной структурой потребуется уточнять список исходников и include-пути. Статическая линковка касается лишь PGR_Make, а реальные компиляторы и CMake поставляются пользователем. Менеджер пока не умеет переименовывать и удалять записи проектов через TUI; автоматический анализ сложных деревьев исходников остаётся эвристическим. Инкрементальная сборка есть через CMake, но не в прямом режиме. Средства отладки, прошивки MCU и преобразования `.elf` в `.hex/.bin` не включены. Приложение не требует Qt, GTK4, сервера или базы данных.

## 8. Переход со старой версии

Старый общий `build_cmake` **не удаляется автоматически**. Новая версия применяет `.pgr_build/<имя>` и сохраняет данные из старого каталога. Пользователь может позже вручную решить, нужен ли старый каталог. Существующие `config.cfg` и `project.pgr` не переписываются при обновлении через `install_to_c_pgr.bat`.

Если сгенерированный `Project/<имя>/generated_cmake` остался от предыдущей версии и не имеет маркера `.pgr_make_generated_owner`, PGR_Make остановит генерацию, чтобы не удалить неизвестное содержимое. После сохранения резервной копии этот каталог можно вручную переименовать, затем запустить генерацию повторно.

`--native-cmake` предназначен для проектов с готовым `CMakeLists.txt` и не переносит автоматически флаги из `config.cfg` в оригинальный CMake-проект: они должны быть предусмотрены исходной конфигурацией CMake (кроме передаваемых компиляторов и toolchain-файла).
